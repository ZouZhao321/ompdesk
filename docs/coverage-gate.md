# 覆盖率门禁

合并检查回答两个问题：这次改动有没有被测试执行过，新增的导出有没有人用。判定入口是
`scripts/coverage-gate.mjs`，判定逻辑全部在 `lib/coverage-gate/`，持续集成只调用
`bun run ci`。

## 命令与步骤

```
bun run coverage:exports     # 规则三：静态引用检查，不跑测试
bun run coverage:gate        # 规则一、二：跑一次带覆盖率的全套测试后判定
bun run coverage:baseline    # 按分叉点重新生成导出基线
bun run ci                   # 完整门禁
```

`ci` 的步骤在一次定义里（`package.json` 的 `scripts.ci`）：

```
typecheck → coverage:exports → coverage:gate → build → smoke:dev
```

- 静态引用检查排在测试之前：源码读不出来或新增导出没有生产引用时，两次测试运行直接
  省掉。
- 整套流程只跑两次测试：`coverage:gate` 内部的本次运行与分叉点基准运行，两次用的是
  `test-command.ts` 里的同一条命令，函数计数才可比。不插桩的 `bun test` 不进流水线，
  本地要单看测试结论时用 `bun run test`。

## 退出码

| 退出码 | 含义 |
| --- | --- |
| 0 | 通过 |
| 1 | 有判定未通过，或豁免清单校验失败，或带覆盖率的测试失败 |
| 2 | 门禁没有跑起来：覆盖率产物缺失、git 读不到分叉点、源码读不出来 |

2 与 1 分开，是为了不让「门禁本身没运行」看起来像「代码没被测到」，也不让它被当成通过。
报告首行写明是哪种情形。

## 环境与取数

判定前固定环境：`OMPDESK_LIVE_SMOKE=0`、`OMPDESK_LIVE_MODEL=0`。真实模型冒烟用例按
`OMPDESK_LIVE_SMOKE === "1"` 判断是否运行，固定为 `0` 后即使持续集成环境里残留了开启
值也不会运行；两次运行看到同一批用例。

默认跳过的用例不计入覆盖率的分子与分母（lcov 只记录被执行的行与函数）。报告里的跳过
数量取自 `bun test` 末尾的统计行（`N pass`、`N skip`、`N fail`）。局限是依赖 Bun 的输出
格式：Bun 1.4 的 junit 产物需要 XML 解析器，仓库里没有这个依赖。升级 Bun 时复核
`test-command.test.mjs` 里的样本；取不到数时报告写明数量未知，不猜测。

## 平台

判定与平台无关：lcov 里的反斜杠路径先统一成 `/`，同一份产物在 Windows 与 Linux 得到
相同结论。持续集成（Linux）是权威结论；Windows 专属分支（路径分隔符、重命名与删除的
句柄竞争）没有回归保护，需要时在本地跑并附记录。

## 三条规则

1. **新增文件与未加载文件**：新增文件里的函数必须全部被调用（`FNH == FNF`）；改动文件
   在覆盖率产物里没有记录时判「文件未被任何测试加载」。零函数的新增文件记不适用。
2. **函数增量**：相对分叉点，`本次FNH - 基准FNH >= 新增函数数` 且 `本次FNF - 基准FNF >= 0`，
   两条都无条件比较：没有新增函数时被调用数同样不得减少。新增的对外函数名还必须出现在
   某个测试文件的导入语句里（被动覆盖的静态检查）。
3. **新增导出**：新增导出必须在生产引用来源里被引用。基线里的存量符号不重复拦；框架按
   文件名或路径调用的导出（路由方法、页面与布局的默认导出、配置文件、命令行入口）跳过。

失真处理在 `rules/distortion.ts`：改名按旧路径取基准；拆分成多个或合为一个时用函数名
集合对应，对应不完整则豁免规则二并退回行覆盖增量；删旧加新且净增量为零时输出「疑似
替换」，转人工豁免。

生产引用来源是仓库里所有不是测试的源码，包含 `scripts/` 与 `bin/`（命令行入口确实使用
被测模块的导出），排除测试文件与 `test-support/`。受管源文件在此基础上再排除 `scripts/`：
这些脚本不被测试加载，进覆盖率分母只会压低数字。

## 豁免清单

仓库根的 `coverage-exceptions.json`，按文件登记，字段全必填、都不能是空字符串：

```json
{
  "exceptions": [
    {
      "path": "lib/legacy/theme.ts",
      "rule": "rule-1",
      "reason": "只做类型声明，测试运行时不会加载",
      "alternativeVerification": "bun run typecheck 覆盖该文件的类型错误",
      "expires": "2026-12-31"
    }
  ]
}
```

同文件同规则只允许一条；到期日当天仍生效，次日起规则重新拦截。清单只校验格式与日期，
理由是否成立由评审判断。

## 基线

`coverage-export-baseline.json` 记录分叉点之前就存在、且当时就没有生产引用的导出（路径、
导出名、种类）。规则三只拦本次新增，命中基线的符号不判失败。

基线必须站在分叉点上生成：拿工作区生成会把本次新增的导出一起收进来，规则三就再也拦不住
自己的改动。`bun run coverage:baseline` 从 `git merge-base origin/main HEAD` 逐个读源码，
只收该提交里存在、没有生产引用、且不属于框架约定的导出。

## 报告

覆盖率报告给出每个改动文件的行与函数数字、仓库内加权合计、产物里缺席的受管源文件、
规则二的两侧对照、失真处理说明、豁免清单与分段耗时（本次测试运行、基准运行、分析，
预算 3 分钟）。静态引用检查单独一屏：改动文件、扫描的生产源文件数、基线条目数、判定明细。
